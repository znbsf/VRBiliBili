```powershell

adb -s <QUEST_SERIAL> shell getprop ro.build.fingerprint

```

当前基础已确定为 PiliPlus；不再把 BiliTVNative 当作并行开发候选。对照组为固定上游提交的原版与空间适配版，Quest 浏览器/B站网页作为网络和输入参考，PiliPlusVR 仅用于核查特定输入补丁的思路。初步调研的版本号保留在历史文档中，正式构建前重新核对来源、ABI、包名、签名和完整依赖锁定结果。原版与分支可能包名相同，优先用独立测试包名做对照，不为测试卸载现有应用或清空数据。

不同应用版本的对照用于选型。补丁因果验证必须同一上游提交、同一配置，只有被测试的补丁不同。

| 素材 | 用途 |

| 本地合法测试 MP4，H.264 + AAC、1080p、30fps | 排除网络和 B 站接口干扰，验证解码与空间输出 |
| 普通公开投稿，720p/1080p、30fps | 匿名或普通账号基础路径 |

固定公开 BV/cid 与素材版本，但日志不得保存带鉴权参数的完整媒体地址。付费/受限内容只使用用户有访问权限的样本。

## 5. 记录什么，而不是只看“流畅”

- 首帧等待时间：冷启动/热启动分开，每个固定样本至少 5 次，记录中位数和范围。网络视频与本地视频分开。
- 视频播放：实际分辨率、帧率、码率、编码、解码器名称与硬解状态；缓冲次数/总时长；播放器 dropped frames；音画同步现象。
- 空间渲染：实际应用与合成器帧率/帧时间、CPU/GPU 占用、内存、温度/降频。不要把 30fps 视频等同于空间渲染只需 30fps，也不要把系统合成帧率当作视频没有丢帧。
- 电量：固定亮度、相同视频、相同网络、相同初始电量区间比较；充电与不充电分开，避免把粗略百分比当成精确功耗。
- 输入：任务完成率、误触/重试、必须摘头显的操作；手柄和手势分别记录。

工具：ADB logcat（按测试包/PID 与时间窗口筛选）、当前 media-kit/libmpv 可取得的播放与解码统计、MQDH、OVR Metrics Tool。如果另行比较 Media3 路径，才使用其 AnalyticsListener。高频详细日志可能影响性能，Release 性能测试应关闭诊断级刷屏；默认避免记录整个设备的无关日志。

## 6. 故障归因顺序

1. 同一内容在 Quest 浏览器/原客户端是否可达；区分账号权限与接口响应。
2. 播放解析是否得到有效音视频轨、正确请求头与未过期地址。
3. 相同内容能否在普通 Android Surface 上播放；本地测试文件能否播放。
4. 空间 Surface 生命周期、尺寸、渲染层、透明 UI 合成是否正确。
5. 单项成功后再看输入冲突、网络恢复和长时热稳定性。

修改一次只验证一个有依据的假设；保留通过的参考构建与可重现步骤。报告区分“源码核查”“模拟器结果”“Quest 实测”“用户舒适度反馈”，不相互替代。

### 最小对照实验

固定视频、画质、网络、设备亮度与坐姿，分别测试：A 关闭弹幕、B 原有平面弹幕、C 河流。每段先做约 10 分钟体验检查，顺序轮换；通过后再做长时观看。精选跳出和朗读分别增加，不一次开启所有效果。

记录：字幕/主画面被遮挡的次数、错误点击/重试、寻找面板是否需要额外转头、用户的阅读轻松度和干扰程度（各自 1–5 分）、空间帧时间、视频丢帧、内存与温度变化。单个用户的评分用于本项目取舍，不能当作普遍舒适度结论。

播放稳定是前提。效果如果增加卡顿、遮挡或阅读负担，应减少密度/深度或保持关闭，不能用视觉新奇抵消基本播放问题。动画密度和深度的设计参数在基线之后调整，不能作为已获得硬件性能保证。
